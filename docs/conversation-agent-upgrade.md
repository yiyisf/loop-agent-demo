## 1. 为什么要升

产品应是「能对话的 Agent，必要时再规划执行」，而不是「先选模式再跑动态工作流的演示」。

主流 Agent（ChatGPT / Claude / Cursor）没有「对话 vs 工作流」开关：用户只说话，系统自己判断这一轮是回答、用工具，还是拆步骤。

当前缺口：

- 对话是 `LoopEngine` 里 `runChatTurn` 后早退，不是主路径。
- 用户被要求选模式，不符合主流操作。
- `auto` 启发式偏工作流，普通一句话也容易出三步 DAG。
- 历史压成 4000 字纯文本，追问质量差。
- 输入只有字符串；输出像「任务结论」而不是对话。
- 视觉是 shadcn 默认紫 + 亮色状态胶囊 + 首页 Sparkles，一眼生成感。

## 2. 产品模型（无模式开关）

```
用户只输入内容
        │
        ▼
  上下文路由（当前句 + 近几轮 + 是否已有计划/产物）
        │
        ├─ conversation：直接说 / Markdown / 工具
        └─ workflow：生成 Plan →（可选确认）→ 执行 → 总结
              结束后仍在同一 Thread
              下一句默认回到 conversation（追问、解释、改写）
              除非新句再次需要多步协作
```

用户**永远不必**选择 chat / auto / plan_first。

内部仍可有 `route: conversation | workflow` 和 `confirmPlan: boolean`，只给 Runtime 用，不进 Composer。

### 路由原则（C1 核心）

默认偏**对话**。升到工作流要有明确信号，而不是「像个任务」。

| 走对话 | 走工作流 |
| --- | --- |
| 问候、解释、翻译、改写、总结上一条 | 对比、调研、迁移、分阶段方案、要落地的多文件产出 |
| 单次计算 / 单次抓取 / 单次问答 | 用户明确说「按步骤做」「先列计划再执行」「分阶段」 |
| 追问已有计划或结果（为什么、改语气、再解释） | 上一轮已是工作流且用户要求继续扩步、重做、再执行 |
| 短问句、看结果 | 明显的多产出、多依赖任务 |

`plan_first` 不再是模式，而是路由附加位：

- 用户说「先给我看计划」「确认后再做」→ `confirmPlan=true`
- 高风险工具即将成批出现且没有自动批准 → 可确认计划
- 其余工作流 **直接执行**

同一 Thread 内可以来回：先闲聊 → 一句「按这个做一份计划并执行」→ 出 DAG → 再问「第三步为什么失败」→ 对话回答。

前端：Composer 只留输入框、发送/停止、模型（多模型时）、必要时「自动批准工具」。**删除模式三段按钮。**

API：`mode` 字段保留一段时间以免旧客户端报错，但 Web 不再传；服务端一律按上下文路由。后续再删。

## 3. 架构（不推翻 Runtime）

```
POST /threads/:id/messages
        │
        ▼
  ConversationEngine          ← 默认路径
        │  先路由（看上下文，不是看用户开关）
        │
        ├─ conversation：文本 / Markdown / 工具 / 之后的 UI 部件
        ├─ workflow：handoff → 现有 LoopEngine
        └─ emit RunEvent
                │
                ├─ 现有 UI Message Stream（本仓库 Web）
                └─ C4：AG-UI Adapter（外部客户端）
```

Event 仍是唯一事实来源。工作流是对话引擎可调用的能力。

## 4. 分阶段

### C0 — 去 AI 味视觉（与 C1 并行，可先做）

见 §6。验收：首页不再是紫块 + 星星；主按钮/用户气泡不再是高饱和紫；状态不再彩虹胶囊满屏。

### C1 — 无模式、上下文自动识别（优先实现）

**用户感知**

- 打开就说话，没有模式开关。
- 「这段报错什么意思」→ 对话气泡里流式 Markdown，不出三步计划。
- 「调研三个方案并对比」→ 自动出计划并执行（或先确认，若用户要求）。
- 同一会话追问带得上上文。

**技术**

- 删除 Composer 模式 UI；`useAgentChat` / `run-store` 不再让用户设 mode。
- 重写 `resolveExecutionRoute`：输入 = 当前句 + 结构化历史 + 线程里是否已有 plan/artifacts；默认 conversation。
- mock 启发式改对话优先（否则 e2e 会全走工作流）。
- `runChatTurn` → 对话引擎：reasoning、工具后继续说、空回复用人话失败。
- `buildHistory`：最近 8–12 轮结构化（用户原文、助手摘要、工具名、计划目标）。
- 无 Plan 时助手区就是对话，不出现「规划中」空壳。
- e2e：去掉「点击先规划」；用措辞驱动路由（问候走对话，强工作流提示走计划）。

**验收**

- 页面上看不到「对话 / 自动 / 先规划」。
- 「你好 / 解释这段 / 把上一条改成表格」不出 Plan。
- 「对比三个库并给出选型建议」仍出 Plan。
- 「先列出计划等我确认再执行」会停在计划确认。
- 刷新后追问仍知道上文。

### C2 — 多形态内容（已同意）

文本 / Markdown / JSON / 小 PDF 抽文本附件；拖拽粘贴；引用条；产物进主会话。图片不做本期必选项。

### C3 — 生成式 UI（已同意）

白名单部件：`table` / `choice` / `metric` / `form`。禁止任意 HTML。点选后作为下一轮输入。

### C4 — AG-UI 协议适配（已同意）

`POST /api/ag-ui` 把 Event 译成 AG-UI SSE。本仓库 Web **不**换成 CopilotKit。

### C5 — 低优先级积压

MCP、前端工具、子 Agent、跨轮记忆摘要。方案保留，本轮不排期。

## 6. 去 AI 味设计（C0）

### 6.1 现在为什么「像 AI 产品」

对照 `globals.css` 与首页：

- **主色是高饱和紫**（`--primary: oklch(0.511 0.262 276)`，hue 277）。这是 shadcn / AI 模板默认色。
- 首页 **Sparkles + 紫色圆角方块**，文案「今天想完成什么任务？」——典型生成式落地页。
- 用户气泡、发送键、Bot 头像、链接、focus ring 全走同一紫。
- 状态胶囊彩虹：success 绿 / warning 橙 / info 蓝 / primary 紫，一屏四种荧光。
- 深色模式仍带紫味（background hue 286），不是石墨灰。
- 圆角偏大（`--radius: 0.625rem` + `rounded-2xl`），卡片像玩具。

主流工具（Linear / Notion / GitHub / Claude）是：**墨色文字 + 纸色底 + 极少强调色**，状态用字重和淡灰，不用糖豆。

### 6.2 方向：Ink / Paper（推荐，只定一版，不提供彩虹主题）

像编辑产品，不像「AI 启动页」。

| Token | 浅色 | 深色 | 意图 |
| --- | --- | --- | --- |
| background | 暖纸白 `oklch(0.985 0.004 85)` | 石墨 `oklch(0.22 0.008 80)` | 去掉紫相 |
| foreground | 近黑墨 `oklch(0.22 0.01 70)` | 暖白 `oklch(0.96 0.005 85)` | 阅读优先 |
| primary / 按钮 / 发送 | 墨色 `oklch(0.28 0.02 70)` | 浅墨 `oklch(0.90 0.01 80)` | **禁止紫、禁止渐变** |
| primary-foreground | 纸白 | 石墨 | |
| muted / 边框 | 低彩暖灰 | 低彩暖灰 | chroma ≤ 0.02 |
| destructive | 干红，降饱和 | 同左 | 只用于真错误 |
| success / warning / info | **不再当大面积徽章底** | 同左 | 状态改成文字 + 极淡底，或单色点 |

强调色若需要（链接、当前会话），用**同一墨色的下划线/左边线**，不要第二品牌色。

### 6.3 组件层面要改什么

| 现在 | 改为 |
| --- | --- |
| 首页 Sparkles + `bg-primary/10` 方块 | 去掉插画/星星。标题改成一句产品说明，例如「会话」或直接只留输入框 |
| 「今天想完成什么任务？」 | 更中性：「写消息，或描述要做的事」 |
| 用户气泡 `bg-primary` 紫底白字 | 浅暖灰底、墨色字（助手无气泡或仅左边线） |
| 发送按钮实心紫 | 实心墨，禁用时淡灰 |
| Bot 圆形紫头像 | 小字标「助手」或极淡灰圆，不要闪闪图标 |
| `StatusPill` 彩色 Badge | 一行次级文字：「进行中 / 已完成 / 需要确认」，最多一个灰点 |
| 计划卡/步骤彩虹描边 | 细灰边 + 状态用文字；进行中用左边线，不用荧光环 |
| 建议卡片四色图标 | 同一套墨色线性图标，无底色块 |
| `rounded-2xl` 大卡片 | 主面 `rounded-md` / `rounded-lg`，少一层「软糖」 |
| focus ring 紫 | 墨色 20% 或 1px 边框加粗 |

**明确不做**：渐变字、光晕、玻璃拟态、紫粉青配色、装饰性网格/粒子、每个空状态一颗星星。

### 6.4 验收

- 截图对比：首页、对话中、工作流计划展开、深色模式。
- 主色 hue 不再落在 260–290（紫段）。
- 源码中首页无 `Sparkles`。
- 用户气泡与发送键对比度仍可读（WCAG AA）。

C0 只动 `globals.css`、首页、气泡、Badge/Status、少量 layout，不改 Runtime。

## 7. 风险（相对初稿的增量）

| 风险 | 缓解 |
| --- | --- |
| 去掉模式后，旧 e2e 要点「先规划」 | 改为用文案触发（「先列出计划等我确认再执行」）或测试 API 仍传内部 flag（仅测试） |
| 路由误判：该出计划却直接闲聊 | 强工作流词表 + 真实模型路由；提供「按步骤做」口头升级，不必开关 |
| 路由误判：闲聊却出三步 DAG | 默认 conversation；mock 与启发式必须对话优先（与现在相反） |
| 用户想强制先看计划 | 靠自然语言，不靠开关；确认卡仍保留 |
| 去 AI 味后对比度不够 | 墨色按钮按 AA 验收，深色用浅墨按钮 |
